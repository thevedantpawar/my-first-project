# Microns V4

V4 did not add an engine. It added the things a med spa owner needs in order to
believe the engine, and the things a founder needs in order to sell it.

Three changes carry the release:

1. **Appointments now carry a value**, and every value says where it came from.
2. **A demonstration clinic** that seeds records rather than dashboard numbers.
3. **A Revenue Command Center and a Recovery screen** built on top of both.

Everything V3 did still happens exactly as it did. No agent, workflow, route,
safety gate or audit path was removed or weakened.

---

## 1. Appointment pricing

`Appointment.price_cents` existed in V3 and was written by nothing, so the
revenue console was structurally incapable of reporting anything but zero.

`app/services/pricing_service.py` fills it at every creation site — the lead
auto-booker, the voice agent, the staff API and the booking-system webhook.

The important part is not that a number gets written. It is that **a recorded
price and an expected price are different claims**, and the row remembers
which one it is:

| Source | Meaning | Stored as |
|---|---|---|
| `recorded` | A booking platform returned it, or staff typed it. Real money. | `extra.price_source = "recorded"` |
| `clinic_price_list` | The clinic's own published value, applied at booking because nothing better existed. A forecast. | `extra.price_source = "clinic_price_list"` |

Rules the code enforces:

- A recorded price overwrites an expected one. Never the reverse.
- A service the clinic has not priced stays `None`. Writing `0` would turn
  *"we don't know"* into *"it is worth nothing"*, which is a different
  sentence and a false one.
- A complimentary consultation is genuinely `0`, and is counted separately
  from unpriced rows so twenty free consults never drag the average ticket
  to nothing.

The provenance lives in the existing `metadata` JSON column, so an in-production
clinic database needs **no migration**.

`ConsoleService.revenue()` reports the split, and its coverage line says how
many rows came from each source — enough for the interface to caption a total
as *projected* rather than *collected* when that is what it is.

### Configuring prices

Point `SERVICE_PRICE_LIST_PATH` at a JSON file. Entries need an explicit
`booking_value` in dollars:

```json
{ "botox": { "label": "Botox", "from": 12, "booking_value": 420 } }
```

`from` is deliberately ignored. It is a starting price, not an appointment
value — Botox at "from $12 per unit" is not a $12 appointment, and treating one
as the other is how a console ends up reporting nonsense.

A malformed or missing file logs a warning and falls back to the built-in
defaults. It never raises: a bad config file must not take the phone line down
mid-call.

## 2. Demo mode

```bash
python -m app.cli demo seed      # load the Glow Aesthetics clinic
python -m app.cli demo status    # what is loaded
python -m app.cli demo clear     # remove it, and only it
```

Then set `DEMO_MODE=true` and `CLINIC_NAME=Glow Aesthetics`.

Roughly 88 patients, 190 appointments, 64 leads, 29 calls and 265 retention
events across about twelve weeks — sized to look like the clinic being sold to,
not a pilot with a dozen patients.

**Nothing is asserted.** No headline figure is written anywhere. If the console
reports five recovered appointments, five appointment rows exist whose patients
had an earlier no-show, a recovery message, and a later booking. Click any
number and the records are there.

**The real engine does the work.** Leads are scored by `LeadService`, not by a
table of pre-baked scores, and hot leads auto-book through the real booking
path. The demo therefore demonstrates the product rather than a description of
it, and changes when the product changes.

**It is not a perfect world.** About 70% of contacted no-shows return and 60%
of contacted dormant clients do. Some misses are never contacted at all. A demo
where everything works is a demo nobody believes.

### Safety

- Seeding and clearing are **refused when `ENVIRONMENT=production`**. There is
  no force flag. A fictional patient in a live clinic database is a
  data-integrity incident that outlives whoever typed the command.
- Every phone number is in the `555-0100`–`555-0199` block reserved for fiction
  in every North American area code.
- Every row is tagged `demo: true` in its metadata.
- `clear` identifies demo rows by tag, never by "looks untagged" — a real
  clinic record also looks untagged, and an earlier version of this code would
  have deleted one. A test now pins that behaviour.
- The console shows a **demonstration banner on every page** whenever demo mode
  is on. It is not dismissible.

### The guided walkthrough

With demo data seeded, the banner offers a ten-step walkthrough that carries a
prospect through the whole revenue loop in about ten minutes: team → enquiry →
qualification → live test → booking → clinical stop → no-show → recovery →
revenue → morning view.

It navigates the **real console showing real seeded records**. There is no
slideshow and no screenshot, so anything the prospect clicks mid-demo works. It
is unavailable unless demo data is present — narrating a real clinic's live
figures as a sales script would be pointing at real people.

## 3. New projections and routes

All read-only, all `GET`, all behind `require_staff`, all audited.

| Route | What it answers |
|---|---|
| `GET /console/api/command-center` | The owner's first screen, in one request |
| `GET /console/api/recovery` | No-shows, cancellations and dormant clients — attempted and won back |
| `GET /console/api/activity` | What the engine actually did, newest first |

### command_center

Composes what already exists rather than recomputing it. It decides what an
owner sees first and delegates every number to the projection that owns it, so
when `revenue()` changes its mind about what counts as recovered, this screen
changes with it.

The headline is **revenue influenced**, never *earned*. Front-desk bookings are
shown but never folded into it, because the engine did not cause them. It
carries a `basis` field — `recorded`, `expected`, `mixed` or `none` — so the
interface can caption the figure truthfully.

### recovery

Every rate carries its denominator. `70%` alone is close to meaningless when
seven out of ten and seven hundred out of a thousand are different clinics, so
the counts travel with it and the interface shows both. An empty period reads
"No recovery messages sent in this period" rather than "0%".

Defaults to a 90-day window: recovery is a slow loop and a 30-day view of a
90-day process understates it.

### activity

Merges retention events, calls, qualified leads and agent-sourced bookings into
one team log. Two constraints:

- **Nothing dated in the future.** Reminders are written ahead of time; a
  reminder scheduled for next Tuesday is not work anyone has done.
- **Names are resolved last.** Patient relationships are `lazy="noload"` by
  design, so rows carry an id through the merge and only the handful that
  survive the slice get one batched lookup. A dashboard has no business
  decrypting a name it will not show.

There is no simulated activity anywhere in this method, and there must never
be. A quiet clinic produces a short list, and a short list is the honest
answer.

## Console

| Page | Change |
|---|---|
| Overview | Rebuilt as the Revenue Command Center |
| Recovery | New |
| All pages | Demonstration banner when demo mode is on |

The command center answers four questions in order — what came in, what
happened today, what needs me, is my team working — and the layout follows that
order literally rather than being a grid of equal cards, which says everything
matters the same amount.

Two smaller fixes worth knowing about:

- The owner's home screen used to tell a med spa owner to "set
  `VAPI_WEBHOOK_SECRET`". It now says the phone system isn't connected. The
  variable name stayed in Settings, where someone might act on it.
- The activity feed was eight consecutive rows of "Reminder sent" — accurate
  and useless. Adjacent identical entries now collapse into one row with a
  count. Only adjacent ones, so nothing is hidden and ordering still reflects
  what happened.

## Testing

```bash
cd backend
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest -q
```

267 tests. V4 added 66 across three files:

| File | Covers |
|---|---|
| `test_pricing.py` | Price provenance, precedence, clinic price lists, malformed config |
| `test_demo_mode.py` | Production refusal, tagging, teardown safety, and the internal consistency of every derived number |
| `test_command_center.py` | Headline composition, rate denominators, future-dated events, PHI masking, empty-clinic behaviour |

The demo-mode tests are the load-bearing ones. They assert that the console's
derived numbers actually fall out of the seeded rows, so the demo cannot
quietly drift into fiction as the projections change.

There is **no JavaScript test runner** in this repository. The console is
verified by rendering it under Playwright and checking for console errors and
horizontal overflow at 1440px and 430px. That is weaker than unit tests and is
listed as a gap below.

## Production checklist

Before a clinic's real data goes anywhere near this:

- [ ] `ENVIRONMENT=production` — this alone refuses demo seeding, disables
      `/docs`, and enables the strict startup checks
- [ ] `DEMO_MODE=false`, and `python -m app.cli demo status` reports nothing
      seeded
- [ ] `ENCRYPTION_KEY` set and **backed up somewhere the app cannot reach**.
      Without it, PHI is unrecoverable
- [ ] `FINGERPRINT_SECRET` and `INTERNAL_API_TOKEN` changed from their defaults
      (the app refuses to start otherwise)
- [ ] `STAFF_API_TOKEN` set to something long and random
- [ ] `SERVICE_PRICE_LIST_PATH` points at the clinic's real prices, or the
      defaults have been reviewed and accepted
- [ ] A BAA is in place with whichever model provider is configured. The Gemini
      Developer API is **not** BAA-covered; the app warns about this on startup
- [ ] `VAPI_WEBHOOK_SECRET` matches the assistant's `serverUrlSecret`
- [ ] Twilio A2P 10DLC registration approved, or SMS stays composed-and-audited
      but undelivered
- [ ] The booking adapter has been exercised against a real account —
      the Acuity and Square adapters are written against documented APIs and
      carry explicit "verify against a sandbox" notes

## Known gaps

Named rather than hidden.

- **No JavaScript unit tests.** The console is verified by rendering, which
  catches breakage but not logic errors.
- **SMS, voice and booking write-back are still not connected** in any
  deployment. The engine composes and audits messages; delivery needs Twilio
  credentials and A2P registration. This is unchanged from V3 and is a
  configuration gap, not a code gap.
- **Every demo price is an expected price.** Nothing in the demo carries a
  price from a booking platform, because no booking platform is connected. The
  console says so.
- **Single-tenant per deployment.** No multi-clinic console.
- **Onboarding is not built.** Configuration is still environment variables and
  the Settings screen.
